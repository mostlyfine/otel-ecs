# AWS ECS上のオブザーバビリティスタック - 設計書

本文書は、オブザーバビリティスタック（Grafana, Mimir, Loki, Tempo, OpenTelemetry）をAWS ECS上にTerraformを用いてデプロイするためのアーキテクチャと設計について概説します。

## 1. 全体アーキテクチャ図

（ここに、各コンポーネントとAWSリソースの関係を示す図を配置します。）

*   **ユーザーアクセス**: ユーザーはApplication Load Balancer（ALB）経由でGrafanaにアクセスします。
*   **データ収集**: アプリケーションはテレメトリデータをOpenTelemetry Collectorに送信します。
*   **データ処理・保存**: Collectorは受信したデータを適切なバックエンドに転送します。
    *   メトリクス -> Mimir -> S3
    *   ログ -> Loki -> S3
    *   トレース -> Tempo -> S3
*   **可視化**: GrafanaはMimir, Loki, Tempoにクエリを発行し、ダッシュボードに情��を表示します。
*   **基盤インフラ**: 全てのコンポーネントは、カスタムVPC内のAWS ECS Fargateクラスター上でサービスとして稼働します。

## 2. 各コンポーネントの役割

*   **Grafana**: 可視化のための主要インターフェース。Mimir, Loki, Tempoをデータソースとして設定します。
*   **Mimir**: Prometheus互換の、スケーラブルなメトリクス用長期ストレージです。
*   **Loki**: 水平方向にスケール可能で、高可用性を持つマルチテナントのログ集約システムです。
*   **Tempo**: 高スケールかつ最小限の依存関係で動作する分散トレーシングバックエンドです。
*   **OpenTelemetry Collector**: テレメトリデータを受信、処理、転送する単一のエージェント。全てのオブザーバビリティシグナルの中心的な入口として機能します。

## 3. データフロー

1.  **メトリクス**: `アプリケーション` -> `OpenTelemetry Collector` -> `Mimir` -> `Grafana`
2.  **ログ**: `アプリケーション` -> `OpenTelemetry Collector` -> `Loki` -> `Grafana`
3.  **トレース**: `アプリケーション` -> `OpenTelemetry Collector` -> `Tempo` -> `Grafana`

## 4. インフラストラクチャ構成

*   **ネットワーク**:
    *   `10.2.0.0/16` のCIDRブロックを持つ新しいVPCを作成します。
    *   高可用性のために、VPCは3つのアベイラビリティゾーン（AZ）にまたがって構築します。
    *   各AZにパブリックサブネットとプライベートサブネットを配置します。
    *   プライベートサブネットからのアウトバウンド通信を許可するため、各AZにNATゲートウェイをデプロイします。
*   **ECS**:
    *   単一のECSクラスターをプロビジョニングします。
    *   全てのオブザーバビリティコンポーネントは、EC2インスタンスの管理が不要なFargateサービスとして実行します。
    *   基盤コンポーネントのログ収集のために、ECSタスク定義でAWS FireLens (Fluent Bit) をログルーターとして設定します。
*   **ストレージ**:
    *   Mimir, Loki, Tempoがデータを保存するために、それぞれ専用のS3バケットを作成します。
*   **IAM**:
    *   ECSタスク実行ロールを1つ作成します。
    *   各コンポーネント（Grafana, Mimir等）には、S3バケットへのアクセス権限など、最小限の権限を持つ専用のIAMタスクロールを割り当てます。
*   **ロードバランシング**:
    *   GrafanaのUIへ安全にアクセスするために、インターネット向けのApplication Load Balancer (ALB)を設置します。

## 5. Terraform実装方針

*   **モジュールの最大限の活用**: 公式の`terraform-aws-modules`を全面的に活用します。VPC, ECS, ALB, S3といった主要コンポーネントとそのサブリソース（ECSサービス、タスク定義、IAMロール、セキュリティグループ）は全てモジュールのパラメータを通じて管理し、ベストプラクティスを遵守しつつ、独自のリソース定義を最小限に抑えます。
*   **動的でポータブルな設定**: `data`ソースを用いて利用可能なアベイラビリティゾーンを動的に取得することで、構成のポータビリティを高めます。
*   **ECSモジュール統合管理**: `terraform-aws-modules/ecs/aws`モジュールを使用して、ECSクラスター、タスク定義、サービスを統合的に管理します。タスク定義もモジュール内で定義し、一貫性のある管理を実現します。
*   **設定の配置戦略**:
    * VPC CIDR: `variables.tf`に配置（環境によって変更可能）
    * AWSリージョン: `locals.tf`に配置（ap-northeast-1 Tokyo、プロジェクト固有設定）
*   **サービスディスカバリ**: 内部ALBとSecurity Groupsを採用。固定的な構成でシンプルかつコスト効率的なアプローチを採用します。
*   **セキュリティグループ**:
    *   **パブリックALB**: Grafanaアクセス用に、インターネット(`0.0.0.0/0`)からのインバウンドHTTPS（ポート443）トラフィックを許可する専用のセキュリティグループを設けます。
    *   **内部ALB**: VPCのCIDRブロック内からの全ポートにおけるインバウンドトラフィックを許可し、サービス間通信を可能にします。
    *   **ECSサービス**: 各コンポーネント（Grafana, Mimirなど）は独自のセキュリティグループを持ち��関連するALB（パブリックまたは内部）からのみインバウンドトラフィックを許可するように設定され、最小権限のネットワーク環境を保証します。

## 6. Terraformファイル構成

最終的なプロジェクト構成は、クリーンで簡潔、かつモジュールベースのアプローチに厳密に従っています。

### 基本設定ファイル
*   `main.tf`: プロバイダとバックエンドの設定。
*   `variables.tf`: 入力変数（VPC CIDR、環境設定、プロジェクト名など）。
*   `outputs.tf`: 出力値（GrafanaのURLなど）。
*   `data.tf`: AWSアベイラビリティゾーンを取得するためのデータソース。

### インフラストラクチャファイル
*   `locals.tf`: 共通設定のみ（AWSリージョン: ap-northeast-1、名前プレフィックス、タグ、S3バケット名）。
*   `network.tf`: `terraform-aws-modules/vpc/aws`を用いたVPCの定義。
*   `s3.tf`: `terraform-aws-modules/s3-bucket/aws`を用いたS3バケットの定義。
*   `alb.tf`: `terraform-aws-modules/alb/aws`を用いたApplication Load Balancerの定義。
*   `ecs.tf`: プロジェクトの中核。`terraform-aws-modules/ecs/aws`モジュールを使用して、ECSクラスター、タスク定義、サービス、IAMロール（S3アクセスポリシーを含む）、セキュリティグループを統合的に定義・管理。
